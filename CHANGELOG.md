# Changelog

## [Unreleased]

- In-app Notifications: the sidebar's bell icon is now live, with a count badge and a `/notifications` page listing what needs attention right now — unreviewed transactions, categories over budget this month, overdue recurring bills, and goals 90%+ funded. Nothing new is computed here: every item re-reads a condition that already has its own dedicated page (review queue, budgets, recurring, goals), so the badge always reflects current reality rather than a stored, dismissible notification log. New Settings → Notifications page (`/settings/notifications`) lets each user toggle which of the four conditions surface for them, opt-out by default (an unset preference reads as enabled). Explicitly in-app only — no email or push, since no delivery infrastructure exists in this app. New `user_notification_preferences` table (one row per user per toggled type) and `App\Services\NotificationService`.

- Tags: freeform labels for transactions, independent of category (e.g. "Reimbursable", "Vacation 2026"). New Settings → Tags page (`/settings/tags`) to create, rename, recolor, and delete tags — deleting one removes it from every transaction that had it (confirmed before submitting). Tags attach to a transaction via a multi-select on the create/edit forms, show as small badges on the transaction list, and are now a filterable dimension on `/reports` alongside accounts and categories. New `tags`/`transaction_tags` tables (the latter existed in the schema since Phase 4a but had no feature built on it); `Request` gained `postArray()`/`queryIntList()`/`postIntList()` helpers for parsing multi-select `name[]` inputs, replacing a private helper that used to live only inside `ReportController`.

- Settings → Categories redesign: categories now render nested under their section (matching the Income/Expenses split already used on the Budgets page) — each `category_group` is its own card with an "Edit" disclosure (rename/delete) in the header, and an "Ungrouped" card catches anything with no section. Category rows dropped the per-category color swatch/picker from this page (colors still exist in the data model and still drive the dot on the Budgets page and other charts — new categories just start uncolored, and existing colors are preserved untouched on save; there's simply no UI here to set one anymore, since the grouped layout carries the visual organization instead). No changes to the underlying category/group data model — this was a view and data-shaping change (`CategoryController::buildSections()`) only.

- Restructured Settings into a proper hub, loosely modeled on the two-column grouped layout common to finance apps (not a copy of any specific one's branding/content/exact layout — see CLAUDE.md's inspiration-not-clone rule). New `/settings/*` area with an "Account" group (Profile, Security — split out of the old combined profile page) and a "Household" group (Members, Categories), each rendered through a shared `resources/views/settings/_nav.php` sub-navigation partial. Profile and Household are no longer separate top-level sidebar destinations (`/profile`, `/household`) — they're reachable through Settings now, matching where a self-hosted single-household app's "my account" and "who's in this household" controls actually belong together. No new features — existing pages moved and gained a consistent home; deliberately skipped adding placeholder tabs for things Finance doesn't have (bank Institutions/Integrations, Merchants, Rules, Billing — most of which would conflict with the Manual-Only Data Policy anyway).

- Phase 8 (Production hardening):
  - **Automated tests**: real PHPUnit coverage where there was almost none before (previously just `RouterTest`/`CsrfTest`). Pure unit tests (no DB — validation, `Money`/`MoneyInput`, `GoalService`, `DebtService`, `CsvParser`, `DashboardWidgets`, financial rounding/bcmath behavior) always run. A new database-backed integration suite (`tests/Integration/`) covers household data isolation (including the IDOR case of a guessed sequential ID), account CRUD, transaction CRUD and duplicate detection, transfer handling, and budget calculations — built on a new `DatabaseTestCase` base class that wraps every test in a rolled-back transaction and refuses to run unless a dedicated test database (name must contain "test") is configured, skipping cleanly instead of risking production data. See `docs/testing.md`.
  - **Security headers**: new `App\Support\SecurityHeaders`, applied to every response — CSP, `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy`, and `Strict-Transport-Security` (only when the request is confirmed HTTPS). No HTTP→HTTPS redirect in code — this app sits behind a Cloudflare Tunnel, where redirecting based on `$_SERVER['HTTPS']` risks a redirect loop; that enforcement belongs in the Cloudflare dashboard instead. See `docs/security.md` for the CSP's documented `unsafe-inline` trade-off (inline `onsubmit` confirm dialogs and dynamic inline `style="width: X%"` progress bars, used throughout the views, would otherwise break).
  - **CSV import hardening**: uploads are now checked against actual file content (`mime_content_type()`), not just the `.csv` extension, which was trivially spoofable.
  - **Backups**: new `bin/backup.sh` — `mysqldump` + `storage/attachments`/`storage/imports`, combined and AES-256-encrypted via `openssl`, refuses to run unencrypted. Not automatic until put on a cron schedule. See `docs/backup-and-recovery.md`.
  - **Documentation**: all 6 previously-missing required docs now exist — `docs/architecture.md`, `docs/database.md`, `docs/api.md`, `docs/security.md`, `docs/deployment.md` (first-time server setup with real `GRANT` statements, production PHP settings, update/rollback procedure, log rotation), `docs/testing.md`. README's status section updated (was stale since Phase 4).
  - Removed unused `SESSION_SECRET`/`SESSION_LIFETIME` from `.env.example` — neither was referenced anywhere in the codebase; kept the README/`.env.example` honest about what's actually configurable instead of guessing at wiring them into new behavior during a hardening pass.

- Phase 11 (Reports): `/reports` — one configurable report instead of a dozen fixed ones, per CLAUDE.md's filter list: custom date range, accounts, categories, transaction type, and household member, with a choice of grouping (category, merchant, account, month, or member). Transfers can be included in the filtered dataset but are always kept out of the income/expense net regardless of grouping, per CLAUDE.md's rule that transfers are never household income or spending — they get their own column. Results export to CSV via `/reports/export` with the same filters. New `ReportingService::transactionsReport()`; `Request` gained `queryArray()` for reading multi-select filter inputs (`account_ids[]`, `category_ids[]`), which the existing scalar `query()` couldn't handle. **Skipped:** tag filtering — `tags`/`transaction_tags` tables exist in the schema but were never built into a usable feature (no repository, no UI to assign a tag to a transaction), so there's nothing to filter by yet.

- Cash Flow (`/cash-flow`): the sidebar's last disabled placeholder is now real. Shows total income, total expenses, and net cash flow for a selectable window (3/6/12/24 months), a combo chart (monthly net cash flow as green/red bars, cumulative total as a line on its own axis so it doesn't get dwarfed by the monthly bars), and a full monthly breakdown table. `ReportingService::incomeVsSpending()` was refactored to share its monthly aggregation query with a new `cashFlow()` method (adds `net` and a running `cumulative` total) rather than duplicating the query — no behavior change for the existing dashboard tile. `charts.js` gained a `cashflow` chart type (mixed bar+line, per-bar coloring by sign via a scriptable Chart.js option).

- Phase 7 (Goals & Debt):
  - **Goals**: `/goals` — savings goals (emergency fund, vacation, debt payoff, etc.) with a target amount, optional target date, optional linked account (reference only, not auto-synced — contributions stay manually logged, matching this app's manual-entry philosophy), and an optional responsible household member. Contributions are logged individually (`goal_contributions`) and atomically update the goal's running `current_amount` (reversible — deleting a contribution reverses it back out), the same denormalized-total-plus-history pattern already used for account balances. New `App\Services\GoalService` computes progress percentage, an estimated completion date from the goal's own planned monthly contribution, and a suggested monthly contribution to hit a target date — every projection is explicitly labeled "(estimate)" in the UI, per CLAUDE.md's instruction never to present these as guaranteed. Goals can be marked complete, archived, or reactivated (never deleted, so contribution history is preserved). New "Goals" dashboard tile.
  - **Debt**: `/debt` — an overview built entirely from data the `accounts` table already had (credit cards, mortgages, auto/student/personal loans): balance, interest rate, minimum payment, due day, and for credit cards, utilization (flagged at 30%+). New `App\Services\DebtService` estimates a payoff date via fixed-payment amortization, clearly labeled "(est.)", and flags accounts where the minimum payment doesn't even cover the monthly interest instead of showing a nonsensical projection. No new table — this is a read-only view over existing account data; balances/rates are still edited from the existing Accounts pages. New "Debt" dashboard tile.
  - New `financial_goals` and `goal_contributions` tables; `Goals` and `Debt` sidebar links (replacing the disabled "Goals" placeholder).

- Per-tile dashboard resize: every tile now has a small resize toggle (next to the drag handle) to switch between full-width and column-width, on top of the existing drag-to-reorder and show/hide customization. Persisted per-user in `users.dashboard_layout` alongside order/visibility (new `wide` key — `null` means "never touched, use each tile's built-in default," distinct from an explicitly-saved empty list). The three new chart tiles default to full width since that's what they need to be readable; every other tile can now also be widened if wanted. New `/dashboard/width` endpoint, shared `dashboard/widgets/_header.php` partial (all 9 real widget tiles now render their header through it instead of duplicating the markup).

- Dashboard charts (Phase 5): three new chart tiles — Net Worth Trend (last 12 months, built from `account_balance_history` per CLAUDE.md's rule against deriving net worth solely from transactions), Income vs. Spending (last 6 months), and Spending by Category (current month, using each category's own color). New `App\Services\ReportingService` houses the aggregation logic, kept out of controllers per CLAUDE.md's "dedicated calculation or reporting services" guidance. Charts render via Chart.js, vendored locally as a static file (`public/assets/js/vendor/chart.umd.min.js`, MIT licensed) — no CDN, no external requests at runtime, consistent with this app's no-third-party-scripts stance. Every chart also renders a visually-hidden (`sr-only`) data table with the same numbers, satisfying CLAUDE.md's "readable alternatives to visual-only information" requirement — screen readers get the real data, not just a canvas. Chart tiles span both dashboard columns for readability and plug into the existing show/hide/reorder customization system like any other tile. **Known simplification:** the net worth trend only includes accounts that are *currently* active and included in net worth — an account archived partway through the 12-month window drops out of every month's figure, not just the months after archiving, so the chart always stays consistent with the current net-worth figure rather than reflecting exactly what was true at each point in time.

- Phase 6b (Recurring bills & subscriptions): track expected recurring income/expenses (bills, subscriptions, paychecks) with an amount, frequency (weekly/biweekly/monthly/quarterly/annually), next due date, account, optional category, auto-pay flag, and notes. `/recurring` shows Overdue and Upcoming lists plus a monthly recurring-cost summary (income and expenses normalized to a monthly-equivalent across frequencies). "Mark paid" creates the matching transaction (pre-reviewed, since confirming payment *is* the review), links it back to the recurring item for a payment-history view, advances the due date from the date that was due (not from today, so cadence doesn't drift if you're late marking something), and updates the expected amount if the paid amount differs — logged to the audit log as a price change. Canceling a recurring item preserves it (and its payment history) instead of deleting it; it can be reactivated later. New "Recurring Bills" dashboard tile and a real "Recurring" sidebar link. `recurring_items` table and `transactions.recurring_item_id` added. **Deferred:** calendar view, and any automatic detection/suggestion of recurring patterns from transaction history (CLAUDE.md requires user confirmation for that regardless, and it's a meaningfully different feature — this release is manual recurring-item definitions only). Reminder settings were also skipped: this app has no notification-delivery mechanism yet (email is stubbed), and a reminder field with no way to actually notify anyone would be a half-finished feature — the Overdue section on `/recurring` and the dashboard tile serve as the in-app equivalent for now.
- Budget sections + income budgeting: categories can now be organized into user-defined sections (e.g. "Fixed Expenses", "Savings") managed on Settings → Categories, separately for income and expense categories. New `category_groups` table and `categories.group_id` (nullable, `ON DELETE SET NULL` so deleting a section un-groups its categories instead of orphaning them). The Budgets page now shows Income and Expenses as fully separate areas, each broken into its sections, with a summary card (planned/actual income, expenses, and surplus). Income categories get the same planned-vs-actual treatment as expenses (`budget_items.category_id` was always type-agnostic; only the application-level validation was expense-only before). `BudgetRepository::actualSpendingByCategory()` was generalized to `actualByCategory($householdId, $type, ...)` to serve both.
- Phase 6 (Budgets): straightforward monthly category budgets, per CLAUDE.md's MVP scope. `/budgets` lets Owner/Administrator set a planned amount per expense category for a given month (Member/Viewer can view but not edit, matching their role permissions); each row shows actual spend for the month against the plan, a progress bar, and how much is over/remaining. "Copy last month" fills in categories that don't already have a line this month from the previous month's budget, without overwriting anything already set. A budget row is only ever created the first time a category gets a planned amount — visiting an empty month never writes anything. Actual spending is computed from transactions directly (excluding transfers and anything marked exclude_from_budget), never stored redundantly, so it's always live. New "Budget" dashboard tile (remaining vs. planned/spent for the current month) and a real "Budgets" sidebar link. `budgets` and `budget_items` tables added.
- Transaction review queue: a dedicated `/transactions/review` page listing every unreviewed transaction, grouped by date ("Today", "Yesterday", then the actual date) so nothing from a missed day gets buried once newer transactions push it off the regular list. Each row has a one-click "Mark reviewed," plus a "Mark all reviewed" bulk action (confirmed before running). New "Needs Review" dashboard tile shows the unreviewed count and flags how many are from before today; a matching "Review" button (with count badge) was added to the Transactions toolbar. The review list is capped at 500 rows as a safety net, with a note if the true unreviewed count is higher.
- CSV import/export for transactions, per CLAUDE.md's explicit workflow (upload → validate → preview + column mapping → confirm → detailed result). Uploaded files are staged in `storage/imports/` under a securely-random token (never the client-supplied filename, ruling out path traversal), parsed and previewed before anything touches the database, and deleted after a successful import. Duplicate detection skips rows matching an existing transaction (same account/date/amount/payee). Balance is adjusted once per import (not once per row) with a single summarizing `account_balance_history` entry. `imports`/`import_rows` tables record every import for audit purposes, including per-row rejection reasons. Export streams the currently-filtered transaction list as CSV. **Known gap:** if a user uploads a file and abandons the flow before confirming, the staged temp file has no automatic cleanup yet — worth a periodic `find storage/imports -mtime +1 -delete` cron or a proper TTL sweep later.
- Phase 4b (Transfers): move money between your own accounts without it counting as income or spending, per CLAUDE.md. Stored as a linked pair of transaction rows (`transfer_pair_id`), both created/deleted atomically in one DB transaction so the two account balances can never desync. Editing a transfer's amount/accounts isn't supported (would require reconciling both sides at once) — instead transfers get a reduced edit view (notes/reviewed only) with a clear "delete this transfer" action that correctly reverses both balances. New `/transactions/transfer` flow, "Transfer" filter option, and transfers show as "Transfer" in the category column since they have none.
- Settings → Categories page: create, rename, recolor, and archive/restore categories from the UI (previously only seedable). New sidebar "Settings" link and a now-functional gear icon in the top icon row (the search/bell/collapse icons next to it stay disabled placeholders — no feature behind them yet).
- Phase 4a (Transactions — income/expense core): categories (with a default set seeded for new households, plus `bin/seed-categories.php` to backfill existing ones), income/expense transaction CRUD with search/filter/pagination, and automatic account balance adjustment — every create/edit/delete runs inside a real DB transaction (`BEGIN`/`COMMIT`, atomic — unlike the migration runner, this is DML so it actually works) that updates `transactions`, `accounts.current_balance`, and `account_balance_history` together or not at all. Amount is entered as a positive number with an Income/Expense selector; the server determines the sign, never trusting a user-typed one. Dashboard's "Recent Transactions" tile is now real. Editing a transaction that moves it to a different account correctly reverses the balance effect on the old account and applies it to the new one. `categories`, `tags`, `transactions`, `transaction_tags` tables added (`tags`/`transaction_tags` reserved for the next increment).
- Deferred to the next increment: transfers (needs paired-transaction linking so they don't count as income/spending), split transactions, CSV import/export, bulk editing, duplicate detection.
- New color theme: terracotta accent (replaces blue) on a warm stone neutral base (replaces cool slate). Added a custom `terracotta` ramp to `tailwind.config.js`; every accent/neutral utility class across all views and `app.css` updated. Semantic colors (red for errors/debt, emerald for success/assets) are unchanged — only brand accent and neutral tones moved.
- "Customize dashboard" modal: toggle switches to show/hide individual tiles, separate from drag-to-reorder. `users.dashboard_layout` now stores `{"order": [...], "hidden": [...]}` instead of a flat array; order and visibility save through independent endpoints (`/dashboard/layout`, `/dashboard/widgets`) so one action can't clobber the other's latest change. Both validate every key against the widget registry server-side.
- Dashboard grid: 2 columns instead of 3, wider tiles.
- Fixed left sidebar layout (`resources/views/partials/sidebar.php`, replaces the old top nav bar) — stays in place while page content scrolls, matching CLAUDE.md's suggested layout. Shows real nav items (Overview, Accounts, Household) plus greyed-out preview items for unbuilt sections (Transactions, Cash Flow, Budgets, Recurring, Goals, Reports), and a user identity + log out footer. User's name/email are now cached in the session (`AuthMiddleware::setUserIdentity()`, refreshed on login, invite-acceptance, and profile updates) so every page can render the sidebar footer without an extra DB query.
- Customizable dashboard: draggable tile grid (native HTML5 drag-and-drop, no JS library) with per-user persisted order (`users.dashboard_layout` JSON column). Real data in the Net Worth and Accounts tiles; honest "Coming soon" placeholders for Spending/Budget/Transactions/Recurring/Goals/Investments until those phases are built. Layout save endpoint validates every tile key against the widget registry server-side (never trusts client-supplied keys).
- Design system: Tailwind CSS compiled to a static `public/assets/css/app.css` (no Node.js required on the server), a shared component layer (cards, buttons, form fields, alerts, badges, tables), dark mode, and a shared authenticated-page nav partial. Every Phase 1/2 view rebuilt against it.
- Router: added dynamic path segments (`/accounts/{id}/edit`) needed for per-record pages, with exact-match routes still taking priority over pattern routes.
- Phase 3 (Financial Accounts): manual account CRUD (checking/savings/credit card/mortgage/loans/investment/property/vehicle/etc.), archive/restore, and balance adjustments with a full audit-trail history (`account_balance_history` — balances are never silently overwritten). All monetary values are `DECIMAL`, never float; all account queries are scoped to the household ID from the session, never a client-supplied one. Dashboard now shows net worth (assets/liabilities via bcmath, not float arithmetic) and an accounts summary. `accounts` and `account_balance_history` tables added.
- Phase 2b/2c (Password reset, profiles, invitations, roles): forgot/reset password flow (email stubbed — reset links are logged, not sent), user profile page (edit name/email, change password with current-password confirmation), household invitations (owner/administrator only, invite-by-email with role selection, 7-day expiring tokens), a working `/household` members page, and `AuthMiddleware::requireRole()` for role-gated actions. Adds an authenticated dashboard nav (Household, Profile, Log out). `password_reset_tokens` and `household_invitations` tables added.
- Phase 2a (Authentication core): login/logout with secure sessions (HttpOnly, SameSite=Lax, Secure over HTTPS, session ID regenerated on login), CSRF-protected login form, per-email/IP login rate limiting (5 attempts / 15 min), audit logging for auth events. Invite-only: no public registration route — first Owner + household are created via `bin/create-owner.php`. `audit_logs` and `login_attempts` tables added.
- Phase 1 (Project Foundation): PDO database connection, migration runner, base routing (`Request`/`Response`/`Router`), global error handling and file logging, `/health` check, PHPUnit setup.
