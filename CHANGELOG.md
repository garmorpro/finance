# Changelog

## [Unreleased]

- Read-only Master HQ reporting API: `GET /api/master-hq/v1/summary`, a single JSON endpoint for one trusted external consumer to build a financial dashboard from, authenticated with a static bearer token (`MASTER_HQ_API_TOKEN`, compared via `hash_equals()`, new `App\Support\MasterHqAuth`) rather than the session-cookie scheme every other endpoint uses — this app had no server-to-server auth pattern to reuse, confirmed by inspecting the whole codebase first. New `MASTER_HQ_HOUSEHOLD_ID` env var explicitly configures which household the token reports on, since a bearer token has no "signed-in household" the way a browser session does; both new vars added to `.env.example` with no values. Every financial figure is produced by the *existing* `ReportingService` (the same class the dashboard/Cash Flow/Reports pages already use) via a new thin `App\Services\MasterHqSummaryService` that only reshapes that output into the API's JSON contract — no financial arithmetic duplicated. The one genuinely new calculation is `ReportingService::dailyIncomeExpense()` (daily granularity; every other trend series in this app was monthly), and `ReportingService::savingsRate()` was extracted from what was previously inline logic in the dashboard's Savings Rate widget so both callers share one formula. `incomeSources` is honestly derived from income-type categories (`type`/`hours`/`effectiveHourlyRate`/`expenses` are `null` or `"other"` throughout — this app has no distinct income-source entity with hours/rate tracking, documented under "Known unsupported metrics" in `docs/api.md` rather than fabricated). New `Request::header()` (nothing in this app previously needed to read an arbitrary request header). Tests: `tests/Support/MasterHqAuthTest.php` (token/bearer-parsing, pure unit) and `tests/Services/MasterHqSummaryServiceTest.php` (integration — income/expense/net/savings-rate/trend/income-source calculations, transfers excluded, zero-income and empty-household behavior, a date-boundary test that derives its expected dates from `gmdate()` at run time so it's correct regardless of which month it runs in, and an explicit assertion that no sensitive/internal field name — account numbers, credentials, internal ids — ever appears anywhere in the response). Full endpoint documentation (auth, schema, date semantics, calculation ownership, example request/response, known limitations) added to `docs/api.md`.

- One-time script `bin/wipe-transactional-data.php`: empties every table except the structural/reference ones needed to keep using the app right after (`accounts`, `categories`, `category_groups`, `households`, `household_members`, `users`, `webauthn_credentials`, plus the `migrations` tracking table) — transactions, budgets, goals, recurring items, imports, rules, tags, sessions, audit logs, and balance history are all wiped via `TRUNCATE`. Refuses to run at all if the database has any table not accounted for in either the keep or wipe list (schema drift since this was written), rather than silently guessing. `FOREIGN_KEY_CHECKS` is disabled only for the duration of `--apply`, since several wiped tables reference each other. Defaults to a dry run listing row counts per table; nothing is deleted without `--apply`.

- Actually fixed passkey registration's `'rp.id' cannot be used with the current origin'` (the previous entry's fix was wrong): confirmed from the real JSON response that `PublicKeyCredentialRpEntity::create()`/`PublicKeyCredentialUserEntity::create()` take `(name, id, ...)` — name first — the opposite of the previous "fix," which was reverted back. The actual root cause was `WebAuthnService::rpId()` resolving to the literal string `"localhost"` instead of the real domain — `$_ENV['APP_URL']` wasn't yielding anything usable on this server, and it was being checked before the browser's own `Host` header rather than after. `rpId()` now reads `$_SERVER['HTTP_HOST']` (stripped of a port, if any) first, since that's guaranteed to match whatever origin the browser is actually on — which is the one thing WebAuthn's `rp.id` must match — with `APP_URL` only as a last-resort fallback.

- Fixed passkey registration failing immediately with `'rp.id' cannot be used with the current origin` — `PublicKeyCredentialRpEntity::create()` and `PublicKeyCredentialUserEntity::create()` both take `id` before `name` per the WebAuthn spec's own field order, and both calls in `WebAuthnService` had it backwards (name first), so the browser was receiving the display string `"MyCFO+"` as the relying party *id* instead of the actual domain. Exactly the kind of mismatch flagged as the likely failure point when this shipped untested.

- Passkey sign-in (Face ID / Touch ID / Windows Hello / platform screen lock), completing the WebAuthn foundation from the previous entry below (dependency, schema, credential repository). Added `App\Services\WebAuthnService` (isolates every `web-auth/webauthn-lib` call in one place), `App\Controllers\WebAuthnController` (registration/authentication ceremonies — JSON-API-style, unlike the app's usual form-post pattern), a "Passkeys" card in Settings → Security to add/remove one, a "Sign in with a passkey" button on the login page, and `public/assets/js/webauthn.js` handling the browser-side ceremony (base64url conversion, `navigator.credentials.create()`/`.get()`). Passkeys are registered as resident/discoverable credentials with `userVerification: required`, which is what lets the login page offer a passkey option before an email is even typed — the browser's own picker enumerates whichever passkeys exist for the site. A passkey satisfies 2FA on its own by default (`users.webauthn_skip_two_factor`) rather than also demanding a TOTP code afterward. `AuthController::completeLogin()` made public so both the password and passkey flows establish a session through the same one place. See `docs/security.md`'s new "Passkeys (WebAuthn)" section for the full design reasoning. **Run `composer update` after pulling** (the dependency was declared but never installed) — and this is the first feature this session that couldn't be verified by static checks alone; the library's exact v4.9 method signatures and JSON shape are implemented from documented patterns, not executed, so a real end-to-end test (register a passkey, log out, sign back in with it) is needed before trusting it.

- Debt payoff comparisons: `/debt` now compares snowball (smallest balance first) against avalanche (highest interest rate first) side by side — months to debt-free, total interest paid, and the payoff order for each strategy, plus a callout for how much interest avalanche saves versus snowball for the household's actual balances and rates. - Dashboard masonry, take 2: replaced the CSS multi-column approach entirely with a JS-computed layout (`dashboard.js`'s `layoutMasonry()`). CSS `columns` + `break-inside: avoid` + `column-span: all` + a box-shadowed child turned out to be a genuinely unreliable combination across browsers — it produced two different rendering artifacts (a ghost border sliver, then a smeared shadow band) at the column-fragment boundary next to a wide tile. The new approach absolutely-positions each tile by hand-tracking column heights (same idea real masonry libraries use), so there's no column boundary for the browser to mis-render a box across in the first place. Tiles start in normal stacked block flow (readable before JS runs) and switch to absolute positioning once `layoutMasonry()` computes their spot; a `ResizeObserver` on each tile re-triggers layout when content changes height after the fact (e.g. a Chart.js canvas finishing its async render), and layout also re-runs on window resize, drag-drop, visibility toggle, and the per-tile width toggle. Also fixed a latent bug where a missing customize-modal element would have silently skipped the resize-toggle listener too, since both used to share one early `return`.

- Transaction Rules engine: Settings → Rules (`/settings/rules`) lets you define automatic categorization rules — e.g. "payee contains Amazon → set category to Shopping, add tag Online." Each rule is a fixed panel of optional conditions (payee/notes contains, amount equals/greater/less than, account is, type is — all ANDed together, at least one required) and actions (set category, rename payee, add tags, mark reviewed, hide from reports — at least one required). Deliberately a fixed panel rather than an open-ended condition/action builder with add/remove rows: covers everything CLAUDE.md asks for (merchant, account, amount, description) with zero JavaScript, at the cost of one rule not being able to hold two conditions on the same field (e.g. "payee contains X OR payee contains Y" needs two separate rules). Rules apply automatically to every new transaction from manual entry, CSV import, and recurring "mark paid" — never to transfers, whose payee/notes are system-generated and whose two legs must stay in sync. Multiple matching rules layer (later rules override category/payee, tags accumulate, reviewed/hide-from-reports flags only ever turn on). Applying a rule to *existing* transactions is a separate, explicit action (`/settings/rules/{id}/apply`) that previews the affected count and requires confirmation before touching history, per CLAUDE.md. New `transaction_rules`, `transaction_rule_conditions`, `transaction_rule_actions` tables; `App\Services\RuleMatchingService` (matching + action resolution + retroactive apply, shared by live application and preview/apply); `TransactionRepository` gained `applyRuleActions()` (a narrow, monotonic override — never blanks a field a rule didn't touch) and `listMatchableForHousehold()`; `TagRepository` gained `addTagsToTransaction()` (additive, unlike the replace-all `setTagsForTransaction()` used by the transaction forms).
